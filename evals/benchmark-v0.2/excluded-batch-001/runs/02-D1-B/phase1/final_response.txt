## Root cause (confirmed, not the operator's hypothesis)

The stall is in the `condition`-based wrappers' wait predicate, not eviction or the user function holding the lock.

Discriminating evidence (scratch script in `$TMPDIR/dn2-evidence/reproduce_regression.py`):
- **Eviction refuted** — cache held 0–1 of 128 entries while the unrelated caller stalled; nothing to evict.
- **"User function holds the cache lock" refuted** — the cache lock was acquirable within 1 ms while the held computation was running (the body is invoked outside the `with lock` block).
- **Actual cause** — the blocked caller's stack was parked in `Condition.wait_for` on a *decorator-global* predicate: `lambda: not pending` (`src/cachetools/_cached.py:24,153`, `_cachedmethod.py:165,279`). One key being computed gated every other key, including already-cached ones, contradicting `docs/index.rst:335` ("prevent concurrent execution … with *identical* parameters, or cache keys").
