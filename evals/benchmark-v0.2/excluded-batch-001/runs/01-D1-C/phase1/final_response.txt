## Root cause

`_condition*` wrappers used a **global** wait predicate, `cond.wait_for(lambda: not pending)`. `wait_for` only returns when *every* in-flight computation finishes, so any held key blocked all other callers — even cache hits for unrelated keys. Callers were never reaching the cache lookup while another key was pending.

The operator's hypotheses were both refuted by discriminating probes (run against the unfixed code):
- **LRU eviction — refuted**: the stall reproduced with a plain `dict` cache (eviction impossible) and for an already-cached key with `LRUCache(128)` headroom.
- **User function holding the lock — refuted**: the cache condition was acquirable (`acquire(blocking=False)`) while the user function ran; `func` executes outside `with lock`.
- **Confirmed mechanism**: cross-key stall in all four variants (cached/cachedmethod × info on/off), with same-key suppression intact. The docs (`docs/index.rst`) already specify per-key waiting ("identical parameters, or cache keys"), so this was a regression against documented behavior.

## Change

One predicate per condition variant (`src/cachetools/_cached.py:24,154`, `src/cachetools/_cachedmethod.py:165,280`):

```python
# only wait for a pending computation of the same key
cond.wait_for(lambda: k not in pending)          # was: not pending
```

8 insertions, 4 deletions across 2 files; no other behavior touched.
