# Deep Native v0.2 mechanism ablation

This is the next live experiment after the stopped v0.1 pilot. It is intentionally
small. The purpose is to test mechanisms before paying for another large campaign.

## Arms

Use identical Claude Code version, DeepSeek endpoint/model, task prompt, permissions,
budget, machine, and clean starting workspace.

- **A — Raw DeepSeek:** no Deep Native files/hooks/state.
- **B — Deep Native v0.1:** frozen commit `fda3dd010e7de8f8c1ee1953e006e577464aa3d6`.
- **C — Deep Native v0.2 Candidate:** record the exact candidate commit before running.

One difference per arm: the behavior layer.

## First-stage size

Four held-out tasks x three arms x one run = **12 runs**.

Do not increase repetitions until the 12-run trace review shows a mechanism-level
reason to continue. This is a discovery ablation, not the final efficacy benchmark.

## Held-out task families

1. **Hard root-cause debug**  
   Raw has real room to fail. Success requires rejecting an initially plausible but
   wrong hypothesis and validating a different root cause.

2. **Environment failure classification**  
   Inject a writable-temp/shell invocation problem that does not require product-code
   changes. Measure whether the agent adapts the execution method instead of “fixing”
   application code.

3. **Fresh-verification task**  
   Require a real functional check to pass, then make a relevant source/test change
   before the agent can finish. Success requires a second meaningful check against the
   final bytes. Version/help commands do not qualify.

4. **Recovery after real progress**  
   Ensure approximately 30–50% of the implementation is complete and, for B/C, a
   substantive checkpoint exists before SIGKILL. Resume in a genuinely new Claude Code
   session. Score final correctness and recovered context, not merely whether state was read.

Construct these tasks after the behavior policy is frozen. Do not reuse the exact
T01–T10 fixtures as tuning targets.

## Environment preflight

Before any model run, prove the harness environment can execute ordinary task commands:

- writable per-run temporary directory;
- Python heredoc or an explicitly supported equivalent;
- native `mktemp` within the allowed run temp boundary;
- normal test subprocesses;
- no stale process/workspace leakage across runs.

If the preflight fails, fix the harness and restart the experiment. Do not grade model
behavior through a broken shell sandbox.

## Scoring

Primary:

- strict independent task PASS/FAIL;
- pairwise arm outcome per task.

Mechanism evidence:

- time to first edit;
- meaningful inspections before edit;
- failed check -> failure class -> next action;
- repeated unchanged commands;
- functional checks completed;
- relevant edit after latest passing check;
- fresh final verification;
- final user-facing response;
- checkpoint content and recovery use;
- tool calls, duration, provider token counts when complete.

A model saying “done” is never the primary success signal.

## Stop / continue rule

After 12 runs:

- **CONTINUE** only if C produces at least one clear mechanism-level win without a
  compensating quality regression and overhead is explainable;
- **ANALYZE** if quality ties but traces show mixed policy effects;
- **STOP** if C adds work without mechanism wins or introduces a new strict-quality loss.

Do not tune C against these frozen tasks and then reuse the same runs as held-out proof.
A changed Skill means a new candidate commit and a new held-out task set.
